# 管理者マニュアル

管理者（ADMIN）と本部担当者（HQ）向けの運用手順です。

| 操作 | 管理者 | 本部担当者 |
|---|:-:|:-:|
| ユーザー管理・アカウント停止 | ○ | × |
| 店舗・ベンダーマスタ管理 | ○ | × |
| 商品マスタの登録・更新 | ○ | ○ |
| 締め時間・理由マスタの管理 | ○ | ○ |
| 発注の登録・修正・確定・承認 | ○ | ○ |
| 操作ログの閲覧・出力 | ○ | ○ |
| ログイン履歴の閲覧 | ○ | × |

---

## 1. 初期セットアップの順序

新規導入時は次の順で登録してください。前のものを参照するため、順序が重要です。

```
1. 店舗マスタ      → 2. ベンダーマスタ  → 3. 商品マスタ
                                          （担当ベンダーを指定するため2の後）
4. ユーザー        → 5. 締め時間        → 6. 理由マスタ
   （店舗・ベンダーを
     割り当てるため
     1,2の後）
```

すべて **マスタ管理** 画面（管理者のみ）から操作します。

---

## 2. 店舗マスタ

**マスタ管理 → 店舗 → ＋ 店舗を追加**

| 項目 | 必須 | 備考 |
|---|:-:|---|
| 店舗コード | ○ | 発注番号に使われます。重複不可 |
| 店舗名 | ○ | 画面表示名 |
| 住所 / 電話番号 | — | |

閉店した店舗は「無効化」してください。**削除ではなく論理削除** のため、過去の発注履歴は残ります。

---

## 3. ベンダーマスタ

**マスタ管理 → ベンダー → ＋ ベンダーを追加**

| 項目 | 必須 | 備考 |
|---|:-:|---|
| ベンダーコード | ○ | 重複不可 |
| ベンダー名 | ○ | |
| 担当者名 / メールアドレス / 電話番号 | — | メールは通知先の参考情報 |

---

## 4. 商品マスタ

**マスタ管理 → 商品 → ＋ 商品を追加**

| 項目 | 必須 | 備考 |
|---|:-:|---|
| 自社商品コード | ○ | 重複不可 |
| JANコード | ○ | |
| 商品名 | ○ | |
| 商品分類 | — | 発注入力の絞り込みに使われます |
| 規格 | — | 例: 1000ml |
| ケース入数 | ○ | **合計数量の計算に使われます**（合計 = ケース入数 × ケース数 + バラ数） |
| 発注単位 | ○ | ケース / バラ / ケース＋バラ |
| 原価 / 売価 | — | 原価未登録は発注時に警告が出ます |
| 担当ベンダー | ○ | **1商品につき1ベンダー。ここで発注の自動振り分けが決まります** |

### 重要な注意点

- **担当ベンダーの指定が発注の自動振り分けを決めます。** 店舗がベンダーを意識せず発注しても、
  商品の担当ベンダーごとに発注が自動的に分割されます。
- **ケース入数を正しく登録してください。** 誤っていると合計数量がずれます。
- 商品マスタを変更しても、**既存の発注明細は登録時点の内容（商品名・規格・ケース入数・原価）を
  保持** しているため、過去の発注が書き換わることはありません。
- 担当ベンダーを変更すると、関連テーブル（`product_vendors`）も自動的に追従します。
  既存の発注の担当ベンダーは変わりません。

### 取扱終了

「適用終了日」を設定するか、無効化してください。無効化した商品は新規発注できなくなります。

## 5. ユーザー管理

**マスタ管理 → ユーザー**（管理者のみ）

### 新規登録

| 項目 | 必須 | 備考 |
|---|:-:|---|
| 氏名 | ○ | |
| メールアドレス | ○ | ログインIDになります。重複不可 |
| 初期パスワード | ○ | 8文字以上 |
| 権限 | ○ | 管理者 / 本部担当者 / 店舗担当者 / ベンダー担当者 |
| 店舗 | 店舗担当者のみ○ | **店舗担当者には必ず指定してください** |
| ベンダー | ベンダー担当者のみ○ | **ベンダー担当者には必ず指定してください** |

**割り当てルール**（違反するとエラーになります）

- 管理者・本部担当者には店舗もベンダーも割り当てられません（全体を見る権限のため）
- 店舗担当者に店舗が未設定だとデータを参照できません
- ベンダー担当者にベンダーが未設定だとデータを参照できません

> 初期パスワードは安全な方法で本人に伝え、初回ログイン後にパスワードを変更してもらってください。

### アカウント停止

退職・担当変更時は **「アカウント停止」** を押します。

- 即座にログインできなくなります
- 過去の発注・履歴・操作ログは残ります（削除されません）
- 自分自身は停止できません

### ロック解除

ログインに5回失敗すると15分間ロックされます（`.env` の `MAX_LOGIN_FAILURES` / `LOCK_MINUTES` で変更可）。
待てない場合はユーザー一覧の **「ロック解除」** を押してください。

ユーザー一覧には **最終ログイン日時** と **ログイン失敗回数** が表示されます。
失敗回数が異常に多いアカウントは、不正アクセスの試行を疑ってください。

## 6. 締め時間の設定

**マスタ管理 → 締め時間**

### 優先順位

```
商品別締め  →  ベンダー別締め  →  システム標準
（最優先）                        （どれもなければこれ）
```

同じ区分内では、特定の納品日を指定した設定（スポット設定）が優先されます。

### 標準設定

| 種別 | 標準 | 意味 |
|---|---|---|
| 概算締め | 納品日の3日前 | ベンダーへの事前情報提供の目安 |
| 最終締め | 納品日前日の12:00 | **これを過ぎると数量を直接変更できません** |
| ベンダー回答期限 | 納品日前日の15:00 | これを過ぎた未回答は「回答期限超過」として集計されます |

### 設定例

**ベンダー別**（日配品のベンダーは締めを早くしたい）

| 項目 | 値 |
|---|---|
| 適用範囲 | ベンダー別 |
| ベンダー | 架空フーズ株式会社 |
| 最終締め | 1日前 10:00 |
| 回答期限 | 1日前 14:00 |

**商品別**（特定商品だけさらに早く締めたい）

| 項目 | 値 |
|---|---|
| 適用範囲 | 商品別 |
| 商品ID | （商品マスタで確認したID） |
| 最終締め | 2日前 09:00 |

### 注意点

- **締め時間は日本時間で入力します**（内部ではUTCで保存されます）。
- 締め時間は **発注登録時に確定** します。あとから締め時間マスタを変えても、
  登録済みの発注の締め時間は変わりません。
- 1つの発注に複数商品が含まれ、商品ごとに締めが異なる場合、
  発注全体には **最も早い締め時間** が適用されます。
- システム標準の締め時間は削除できません（更新は可能）。

## 7. 理由マスタ

**マスタ管理 → 理由**

変更理由・欠品理由の選択肢を登録します。
現場が入力しやすい表現で登録してください（例: 「売上予測の変更」「天候による需要変動」「生産遅延」）。

## 8. 日々の運用

### ダッシュボードの見かた

ログイン後の最初の画面です。上部でベンダー・店舗・納品日を切り替えると、
すべての数字が連動して絞り込まれます。

| タイル | 対応すべきこと |
|---|---|
| ⏰ 本日締め | 本日締めの発注。締め前に店舗の入力漏れがないか確認 |
| ✎ 未確定 | 下書きのまま放置されている発注。店舗に確定を促す |
| ⏳ ベンダー未確認 | ベンダーがまだ見ていない。回答期限が近ければ連絡 |
| ⚠ 回答期限超過 | **要対応。** ベンダーに直接確認 |
| ✖ 欠品 | 代替手配・店舗への連絡を検討 |
| ◐ 一部納品 | 不足分の対応を検討 |
| ⇄ 代替提案 | **承認・却下が必要** |
| 📝 変更申請 | **承認・却下が必要** |

### 締め後変更申請の承認

1. メニューの **「変更申請」** を開きます。
2. 「申請中」の申請を確認します。変更前数量・申請数量・変更理由・申請者が表示されます。
3. **承認** を押すと数量が更新され、変更履歴に記録されます。ベンダーにも通知されます。
4. **却下** の場合は **却下理由が必須** です。理由は申請者に通知されます。

> 承認するまで数量は変わりません。承認は取り消せないため、内容をよく確認してください。

### 代替商品の承認

ベンダーから代替提案があると通知が届きます。

1. 発注明細画面で代替提案の内容（商品名・数量・原価・納品可能日）を確認します。
2. 承認すると代替商品での納品が確定します。
3. 却下すると欠品扱いに戻ります。

判定は一度きりです。承認・却下後は変更できません。

## 9. データ出力

**出力** メニューから、Excel / CSV / 印刷（PDF）で出力できます。
出力範囲は画面上部の切替（ベンダー・店舗・納品日）に連動します。

| 出力 | 用途 |
|---|---|
| ベンダー別発注一覧 | ベンダーへの発注書送付。Excelはベンダーごとにシートが分かれます |
| 店舗別発注一覧 | 店舗ごとの確認。Excelは店舗ごとにシートが分かれます |
| 商品別集約 | 商品ごとの合計数量。仕入計画に使用 |
| 納品日別集約 | 納品日ごとの状況把握 |
| 欠品一覧 / 一部納品一覧 | 対応漏れの確認 |
| 未回答一覧 | 期限超過フラグ付き。ベンダーへの督促に使用 |
| 変更申請一覧 | 締め後変更の記録 |
| 発注変更履歴 | 監査対応。締め前／締め後の区別付き |
| 操作ログ | 監査対応 |

- **CSV は BOM 付き UTF-8** なので Excel で開いても文字化けしません。
- **PDF は印刷用の画面** が新しいタブで開きます。ブラウザの印刷ダイアログから
  「PDFとして保存」を選んでください。
- **出力操作もすべて操作ログに記録されます**（誰がいつ何を出力したか）。
- 店舗ユーザー・ベンダーユーザーが出力した場合も、自分の範囲のデータのみが出力されます。

## 10. 監査・トラブル対応

### 「言った・言わない」の確認

**履歴** メニューから確認します。

| 確認したいこと | 見る場所 |
|---|---|
| 数量が誰にいつ変えられたか | 履歴 → 数量変更履歴（締め前／締め後の区別あり） |
| 発注がいつ確定したか | 履歴 → ステータス履歴 |
| ベンダーが何と回答したか | 履歴 → ベンダー回答（訂正前の回答も残っています） |
| 誰がどんな操作をしたか | 履歴 → 操作ログ |
| 通知が届いたか | 履歴 → 通知履歴（送信結果つき） |
| 不正ログインの試行 | 履歴 → ログイン履歴（管理者のみ） |

**これらの履歴は削除できません。** 削除するAPIも画面も用意されていません。

### よくある問い合わせ

| 症状 | 原因と対処 |
|---|---|
| 店舗から「修正できない」と連絡 | 締め時間を過ぎています。変更申請を案内してください |
| ベンダーから「発注が見えない」と連絡 | 店舗が一時保存のままの可能性。未確定件数を確認してください |
| 発注が意図しないベンダーに割り振られた | 商品マスタの担当ベンダーを確認してください |
| 合計数量が合わない | 商品マスタのケース入数を確認してください |
| ログインできない | ロック状態を確認し、必要ならロック解除してください |
| 「他の担当者がこの発注を更新しました」と出る | 2人が同時に同じ発注を編集しています。最新を読み込んでからやり直すよう案内してください |
| 「この発注は既に他の担当者が確定しました」と出る | 同時操作です。一覧を再読み込みすると確定済みになっています |
| ベンダー回答後に店舗が数量を直せない | 仕様です。回答の前提が崩れるため、本部が取消して発注し直してください |
| メール通知が届かない | `.env` の `MAIL_ENABLED` と SMTP 設定を確認。通知履歴で送信結果を確認できます |

## 11. バックアップとリストア

PostgreSQL 運用時の手順です。`./backups` が `db` コンテナにマウントされています。

**バックアップ**

```bash
./scripts/backup.sh
```

- 出力先は `./backups`（`BACKUP_DIR` で変更可）
- 30日より古いものは自動削除（`RETENTION_DAYS` で変更可）
- 中身が空の場合は失敗として扱い、壊れたファイルを残しません

cron での定期実行:

```cron
30 2 * * * cd /opt/vendor-order-app && ./scripts/backup.sh >> /var/log/order-backup.log 2>&1
```

**リストア**

```bash
./scripts/restore.sh ./backups/order_app_20260729_023000.sql.gz
```

- 実行前に確認を求めます（`restore` と入力）
- **復元前の状態を自動で退避** してから実行します
- アプリと通知ジョブを停止 → 復元 → マイグレーション適用 → 再起動 まで行います

> バックアップファイルには取引情報が含まれます。保管場所のアクセス権を制限してください。

## 12. 定期的に確認すること

| 頻度 | 確認内容 |
|---|---|
| 毎日 | ダッシュボードの「回答期限超過」「変更申請」「代替提案」 |
| 毎日 | 通知ジョブ（`notifier` コンテナ）が動いていること（`docker compose ps`） |
| 毎週 | 未確定のまま残っている発注、バックアップの取得状況 |
| 毎月 | 操作ログの確認、退職者アカウントの停止漏れ |
| 随時 | ログイン失敗回数が多いアカウント（不正アクセスの兆候） |
