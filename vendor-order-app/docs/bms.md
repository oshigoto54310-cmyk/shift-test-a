# 流通BMS対応へ進む場合の追加課題一覧

本アプリは **MVP段階では流通BMSに接続していません。** 本格対応に進む場合に
検討・実装が必要になる項目を整理します。

> 流通BMS（流通ビジネスメッセージ標準）は、流通業界の企業間取引を
> インターネット経由の標準メッセージで行うための規約です。
> 対応にあたっては最新の標準仕様書を必ず参照してください。
> ここに記載する内容は設計上の論点整理であり、仕様の代替にはなりません。

---

## 1. 前提として必要な準備

| 項目 | 内容 |
|---|---|
| 標準仕様書の入手 | 対象バージョン（基本形／頻度対応形など）と適用メッセージの確定 |
| 取引先との合意 | どのメッセージを、どの頻度で、いつから交換するか |
| GLN の取得 | 事業所コード（GLN）の取得と、店舗・ベンダーへの割り当て |
| 商品コードの整備 | JAN（GTIN-13）の正確性確認、ケースコード（GTIN-14）の要否確認 |
| 接続方式の決定 | JX手順 / ebMS2.0 のどちらを使うか（取引先ごとに異なる場合あり） |
| 通信テスト環境 | 取引先との接続テスト計画 |

## 2. データモデルの拡張

現在のモデルに不足している項目です。

### 2.1 事業所コード（GLN）

| テーブル | 追加カラム | 内容 |
|---|---|---|
| `stores` | `gln` | 店舗のGLN（13桁） |
| `stores` | `delivery_gln` | 納品先GLN（店舗と異なる場合） |
| `vendors` | `gln` | ベンダーのGLN |
| （新規）`companies` | | 自社（発注者）のGLNと事業所情報 |

現在は社内コード（`stores.code` / `vendors.code`）のみのため、
**GLN の追加とコード変換テーブルが必須** です。

### 2.2 商品コード

| テーブル | 追加カラム | 内容 |
|---|---|---|
| `products` | `gtin13` | 現在の `jan_code` を正式名称に整理 |
| `products` | `gtin14` | ケース単位のGTIN（集合包装用商品コード） |
| `products` | `vendor_product_code` | ベンダー側の商品コード |
| `product_vendors` | `vendor_product_code` | （既存カラム。ベンダーごとの商品コード） |

**課題**: ケース発注の場合、BMSでは GTIN-14 とケース入数を送る必要があります。
現在は `jan_code` と `case_qty` のみで GTIN-14 を保持していません。

### 2.3 取引番号

| 項目 | 内容 |
|---|---|
| 発注番号 | 現在は `YYYYMMDD-店舗コード-連番`。BMS仕様の桁数・体系に合わせる必要あり |
| 発注明細番号 | 明細行番号の採番ルールを定義 |
| 出荷番号 / 受領番号 / 請求番号 | 新規に採番体系が必要 |
| メッセージID | 送受信メッセージの一意識別子 |

**課題**: 発注番号は取引先との照合キーになるため、**あとから体系を変えるのは困難** です。
BMS対応の可能性がある場合、早い段階で桁数・体系を決めておくべきです。

### 2.4 単価・金額

| 項目 | 現状 | BMS対応で必要 |
|---|---|---|
| 原価 | `products.cost` / `order_items.cost` | 単価が「税抜」か「税込」かの区分 |
| 税区分 | なし | **消費税区分（標準／軽減）が必須** |
| 税率 | なし | 適用税率 |
| 金額端数処理 | なし | 端数処理区分（切捨／切上／四捨五入）の合意 |
| 通貨 | なし | 通常JPY固定 |

**課題**: 食品小売業では軽減税率対象商品が多く、**税区分の追加は必須** です。
現在のモデルには税に関するカラムがまったくありません。

## 3. 対応が必要なメッセージ

| メッセージ | 方向 | 現状の対応 | 追加作業 |
|---|---|---|---|
| 発注（Order） | 自社 → ベンダー | 発注データは保持済み | メッセージ生成・送信、GLN/GTIN対応、税区分追加 |
| 発注訂正・取消 | 自社 → ベンダー | 変更申請・取消は実装済み | 訂正メッセージへの変換、訂正回数の管理 |
| 出荷（Despatch） | ベンダー → 自社 | **未対応** | 出荷データの受信・保管、発注との突合 |
| 受領（Receiving） | 自社 → ベンダー | **未対応** | 検品機能の実装が前提（roadmap 5） |
| 返品（Return） | 自社 → ベンダー | **未対応** | 返品業務の設計から必要 |
| 請求（Invoice） | ベンダー → 自社 | **MVP対象外** | 請求処理の設計から必要 |
| 支払（Payment） | 自社 → ベンダー | **MVP対象外** | 支払処理の設計から必要 |

現在のアプリが持つ「ベンダー回答（一部納品・欠品・代替提案）」は、
**流通BMSの標準メッセージには直接対応しません。** BMSでは欠品情報は
出荷メッセージ（実際に出荷した数量）で表現されるのが基本です。

**課題**: 現在の「回答」中心の業務フローと、BMSの「出荷実績」中心のフローには
考え方の差があります。両者をどう共存させるか（回答は社内運用として残し、
BMSは出荷データで処理するなど）の業務設計が必要です。

## 4. 通信基盤

### 4.1 接続方式

| 方式 | 内容 | 課題 |
|---|---|---|
| JX手順 | HTTP/SOAP ベース。中小規模向け | クライアント実装、証明書管理 |
| ebMS2.0 | 大企業間で利用 | 実装が複雑。専用製品の導入が現実的 |

**課題**: どちらも独自実装は負担が大きく、**EDIサービスプロバイダの利用を
検討すべき** です。その場合、プロバイダのAPI仕様に合わせた連携部分の実装が必要になります。

### 4.2 セキュリティ

| 項目 | 内容 |
|---|---|
| クライアント証明書 | 取得・更新・失効管理の運用 |
| TLS | 相互認証の設定 |
| 鍵の保管 | 現在の `.env` 方式では不十分。KMS / Vault 等の検討 |

### 4.3 通信の信頼性

| 項目 | 内容 |
|---|---|
| 再送制御 | 送信失敗時のリトライとバックオフ |
| 重複排除 | メッセージIDによる冪等性の担保（現在の `idempotency_keys` の考え方を拡張） |
| 順序保証 | 発注と訂正の到着順序が入れ替わった場合の扱い |
| 送達確認 | 受信確認メッセージの管理 |
| 障害時の運用 | 通信断が続いた場合の代替手段（FAX等）と、復旧後の整合性確認 |

## 5. 新規に必要なテーブル

```
edi_messages          送受信メッセージの記録（メッセージID、種別、方向、状態、本文、送受信日時）
edi_message_errors    エラー内容と再送履歴
edi_partners          取引先ごとの接続設定（GLN、接続方式、証明書、有効期間）
edi_code_mappings     社内コード ⇔ BMSコードの変換表
despatches            出荷データ（ベンダーから受信）
despatch_items        出荷明細
receivings            受領データ
receiving_items       受領明細
tax_categories        消費税区分マスタ
```

## 6. 業務運用面の課題

| 課題 | 内容 |
|---|---|
| 締め時間との整合 | BMSでは取引先ごとに送信時刻が決まる。現在の締め時間設定と整合させる必要がある |
| 訂正の扱い | 現在の「変更申請 → 承認」フローと、BMSの発注訂正メッセージの対応関係を定義する |
| 欠品情報の扱い | BMSでは出荷データで表現される。現在の「欠品回答」との二重管理を避ける設計が必要 |
| 代替商品 | BMSの標準メッセージに代替提案の枠組みがない。社内運用として残すか、別手段を用意する |
| BMS未対応ベンダー | 全ベンダーが対応するとは限らない。**BMS経由と画面経由を併存させる設計が必須** |
| 移行期間 | 並行稼働期間の二重入力・突合作業 |
| テスト | 取引先ごとの接続テスト。本番データを使えないためテストデータの整備が必要 |

**もっとも重要な課題**: 中小ベンダーはBMS未対応であることが多いため、
**「BMS対応ベンダー」と「本アプリ画面で回答するベンダー」が混在する前提** で
設計する必要があります。現在のアプリはこの「画面で回答するベンダー」に対応しており、
BMS対応はそこに加える形になります。

## 7. 段階的な進め方の提案

```
第1段階  現行アプリの安定運用
         ・締め時間通知の定期実行を追加
         ・納品実績（検品）機能を追加  ← BMS受領メッセージの前提
         ・税区分カラムを追加          ← あとから入れると影響が大きい

第2段階  データ整備
         ・GLN の取得と登録
         ・GTIN-14 の整備
         ・発注番号体系の見直し        ← 運用開始後の変更は困難

第3段階  1社での試行
         ・EDIサービスプロバイダの選定
         ・発注メッセージの送信のみ実装
         ・1ベンダーと接続テスト

第4段階  拡大
         ・出荷・受領メッセージの対応
         ・対応ベンダーを順次拡大
         ・BMS経由と画面経由の併存運用

第5段階  請求・支払
         ・請求処理の設計と実装（MVP対象外の領域）
```

## 8. 現行設計がBMS対応で有利な点

将来の対応を見据えた作りになっている部分です。

| 項目 | 内容 |
|---|---|
| 発注明細のスナップショット | 発注時点の商品情報を保持しているため、送信内容の再現が可能 |
| 履歴の完全保存 | 変更履歴・ステータス履歴が削除されないため、訂正メッセージの根拠を追える |
| `product_vendors` テーブル | ベンダーごとの商品コード（`vendor_product_code`）を持てる構造が既にある |
| 冪等性の仕組み | `idempotency_keys` の考え方をメッセージIDの重複排除に流用できる |
| API とフロントの分離 | EDI連携をバックエンドに追加しても画面側の変更が最小限で済む |
| 締め時間の階層設定 | 取引先ごとの送信時刻設定に拡張しやすい |

## 9. 見積もりの目安

規模感の参考です（要件により大きく変動します）。

| 段階 | 主な作業 | 目安 |
|---|---|---|
| 第1段階 | 検品機能、税区分追加、通知バッチ | 1〜2か月 |
| 第2段階 | GLN/GTIN整備、番号体系見直し | 1か月＋データ整備作業 |
| 第3段階 | プロバイダ選定、発注送信、1社接続テスト | 2〜3か月 |
| 第4段階 | 出荷・受領対応、ベンダー拡大 | 3〜6か月 |
| 第5段階 | 請求・支払 | 別途検討 |

**データ整備（GLN取得、GTIN-14の確認、商品マスタの精査）に想定以上の工数がかかる**
ことが多いため、早めに着手することをおすすめします。
