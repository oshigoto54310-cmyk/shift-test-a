# セキュリティ上の注意点

## 実装済みの対策

### パスワード

- **平文保存していません。** bcrypt（コスト12、ソルト自動生成）でハッシュ化しています。
- ログイン失敗が既定5回続くと15分間ロックします（`MAX_LOGIN_FAILURES` / `LOCK_MINUTES`）。
- ログイン失敗メッセージは「メールアドレスまたはパスワードが正しくありません」で統一し、
  アカウントの存在有無を漏らしません。
- パスワード再設定APIも、アカウントの有無にかかわらず同じメッセージを返します。
- 再設定トークンは有効期限1時間の使い捨てです。

### セッション

- JWT を **httpOnly Cookie** に格納します。JavaScript から読めないため、
  XSS でトークンを盗まれるリスクを下げています。
- 有効期限は既定8時間（`SESSION_MINUTES`）。
- `SameSite=Lax` を設定しています。
- `COOKIE_SECURE=true`（本番必須）で HTTPS 経由でのみ送信されます。
- **ログアウトでトークンを失効させます。** Cookie を消すだけでは、
  すでに流出したトークンを使い続けられてしまうため、トークンID（`jti`）を
  `revoked_tokens` に登録してサーバー側で拒否します。他端末のセッションは維持されます。
- **パスワード変更・パスワード再設定・権限や所属の変更・アカウント停止では、
  そのユーザーの全セッションを失効させます。** `users.session_version` を +1 し、
  古い版数を持つトークンを拒否します（時刻比較では JWT の `iat` が秒単位のため
  同じ秒に発行されたトークンを取りこぼすので、版数で判定しています）。

### CSRF

ダブルサブミットクッキー方式を採用しています。

1. ログイン時に `csrf_token` Cookie（httpOnly でない）を発行
2. 更新系リクエスト（POST / PUT / PATCH / DELETE）では `X-CSRF-Token` ヘッダが必須
3. Cookie とヘッダの値を定数時間比較（`hmac.compare_digest`）し、不一致なら 403

Cookie を使わない Bearer 認証のクライアントは CSRF の対象外です。

### XSS

- フロントエンドは DOM に文字列を入れる前に必ず `UI.esc()` でエスケープします。
- レスポンスヘッダに Content-Security-Policy を設定しています。

  ```
  default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline';
  script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
  ```

- `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、
  `Referrer-Policy: same-origin` を設定しています。

### SQLインジェクション

SQLAlchemy ORM のパラメータバインドのみを使用し、SQL文の文字列連結は行っていません。
検索の部分一致も `LIKE` のバインド変数経由です。

### 権限制御

- **すべての更新操作に権限確認を入れています。** 権限外は 403 を返します。
- 参照も `build_scope()` を必ず通し、店舗・ベンダーの絞り込みをサーバー側で強制します。
- URL や API パラメータを書き換えても、権限外のデータには到達できません。
- 出力（Excel / CSV / PDF）にも同じスコープを適用しています。
- これらは自動テスト（`tests/test_permissions.py`、`tests/test_exports.py`）で検証しています。

### 秘密情報の管理

- 秘密鍵・DBパスワード・SMTPパスワードはすべて環境変数から読み込みます。
- `.env` は `.gitignore` に登録済みです。証明書（`certs/`、`*.key`、`*.pem`）も除外しています。
- ソースコードに秘密情報をハードコードしていません。

### 同時更新・競合

- 発注の更新は **楽観ロック**（`orders.version`）で制御します。
  他の担当者が先に更新していると 409 を返し、静かな上書きを防ぎます。
- 発注確定・変更申請の承認・発注取消は **条件付きUPDATEの更新行数**で勝者を決めます。
  「読んで判定してから書く」方式では、同時リクエストが全員判定を通過して
  多重確定・多重承認が起きるためです。
- 発注番号の採番が衝突した場合は、番号を採り直して再試行します。
- これらは `tests/test_concurrency.py` で並列実行して検証しています。

### 監査証跡

- 操作ログ（`audit_logs`）とログイン履歴（`login_logs`）を記録します。
- 取引履歴（数量変更・ステータス変更・ベンダー回答・変更申請）は **追記のみ** で、
  削除するAPIも画面も存在しません。
- マスタと発注は論理削除のみで、物理削除しません。

### 通信

- 本番は HTTPS 前提です。`nginx.conf` に HTTP → HTTPS リダイレクトと
  HSTS（`max-age=31536000`）の設定例を用意しています。

### 実行環境

- Docker コンテナは root ではなく `appuser` で実行します。
- PostgreSQL は既定で外部ポートを公開していません（`docker-compose.yml` でコメントアウト）。

## 本番導入前に必ず行うこと

### 1. SECRET_KEY の変更（最重要）

既定値のままだと **誰でもセッショントークンを偽造できます。**

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

生成した値を `.env` の `SECRET_KEY` に設定してください。

> `SECRET_KEY` を変更すると既存のセッションはすべて無効になります（再ログインが必要）。

### 2. HTTPS の有効化

```dotenv
COOKIE_SECURE=true
ENVIRONMENT=production
```

証明書を `certs/` に配置し、`docker compose --profile https up -d` で起動してください。

> `COOKIE_SECURE=true` のまま HTTP でアクセスすると Cookie が送信されず、ログインできません。
> 必ず HTTPS 経由でアクセスしてください。

### 3. 初期パスワードの変更

`seed.py` が作るアカウントは全て `Password123!` です。
**本番環境で `seed.py` を実行しないでください。** 実行してしまった場合は、
全アカウントのパスワードを直ちに変更してください。

### 4. データベースパスワードの変更

`.env` の `POSTGRES_PASSWORD` を推測困難な値にしてください。

### 5. ENVIRONMENT=production の設定

開発モードでは起動時にテーブルを自動作成します。
本番では Alembic のみでスキーマを管理するため、必ず `production` を設定してください。

### 6. CORS の確認

フロントエンドを同一オリジンで配信する場合、`CORS_ORIGINS` は空のままにしてください。
別ホストで動かす場合のみ、**具体的なオリジンを列挙** してください（`*` は使わないこと）。

## 運用上の注意

### 定期的に確認すること

| 頻度 | 内容 |
|---|---|
| 毎日 | ログイン失敗が多いアカウント（不正アクセスの兆候） |
| 毎週 | バックアップの取得状況 |
| 毎月 | 操作ログの確認、退職者アカウントの停止漏れ |
| 随時 | 依存パッケージの脆弱性（`pip list --outdated`、`pip-audit`） |

### アカウント管理

- 退職・担当変更時は速やかにアカウントを停止してください。
- 管理者権限は必要最小限の人数に限定してください。
- アカウントの共有（同じIDを複数人で使う）は避けてください。操作ログの追跡ができなくなります。

### バックアップ

- バックアップファイルには取引情報が含まれます。保管場所のアクセス権を制限してください。
- 定期的にリストアを試し、実際に復元できることを確認してください。

## 現時点の制約と残課題

導入前に検討すべき点を正直に記載します。

### 1. パスワードポリシーが最小限

現在の制約は「8文字以上」のみです。
文字種の混在や辞書攻撃対策（既知の流出パスワードの拒否）は実装していません。
運用ルールで補うか、`schemas.py` の `PasswordResetConfirm` / `UserIn` に検証を追加してください。

### 2. 二要素認証（2FA）は未実装

管理者アカウントには TOTP などの追加認証を検討してください。

### 3. レート制限が未実装

ログイン試行のアカウントロックはありますが、**IPアドレス単位のレート制限はありません。**
多数のアカウントに対する総当たり攻撃や、APIの大量リクエストは防げません。
リバースプロキシ側（nginx の `limit_req`）での対策を推奨します。

```nginx
limit_req_zone $binary_remote_addr zone=login:10m rate=10r/m;

location /api/auth/login {
    limit_req zone=login burst=5 nodelay;
    proxy_pass http://app:8000;
}
```

### 4. パスワード再設定トークンの伝達

現在はメール本文にトークンを平文で記載します。
メールが傍受された場合のリスクがあるため、有効期限をさらに短くするか、
別経路での本人確認を組み合わせることを検討してください。

### 5. 監査ログの改ざん対策

削除APIは設けていませんが、**データベースに直接アクセスできる者は改ざんできます。**
厳密な監査要件がある場合は、追記専用ストレージへの転送や、
ログのハッシュチェーン化を検討してください。

### 6. 依存パッケージの脆弱性

`requirements.txt` はバージョンを固定しています。
定期的に更新し、脆弱性情報を確認してください。

```bash
pip install pip-audit
pip-audit -r backend/requirements.txt
```

### 7. 個人情報の取り扱い

ユーザーのメールアドレス・氏名・電話番号を保持します。
社内規程や個人情報保護法に沿った運用（保管期間・アクセス権限・退職者データの扱い）を
定めてください。ユーザーの論理削除ではメールアドレスは残ります。
完全な消去が必要な場合は、別途匿名化処理を実装してください。
