## 3. 権限・データ分離の検証（監査前から良好）

### 3-1. 手法

全エンドポイント × 全ロール（管理者・本部・店舗A/B・ベンダーA/B・未認証）の
総当たりプローブを実施。攻撃パターンは URL の ID 書き換え、
クエリパラメータの `vendor_id` / `store_id` 書き換え、リクエストボディの改ざん、
他社の連番ID直接指定、出力API の直接呼び出し。

**判定は「名前が含まれるか」ではなく、レスポンス各行の `store_id` / `vendor_id` が
呼び出し元の許可範囲内かを機械的に照合** した。
（初回は名前一致で判定したが、店舗ユーザーが自店舗の他ベンダー向け発注を見るなど
正当なケースを誤検知したため、行レベル照合に切り替えた。）

### 3-2. 結果

**漏洩ゼロ。** 検証したのは以下。

| 検証対象 | 結果 |
|---|---|
| JSON一覧9種 × 5ロール | 全行がスコープ内。他社IDの明示指定は 403 |
| CSV出力9種 × 5ロール | 全行がスコープ内 |
| 単一リソース直接アクセス | 他店舗・他ベンダーは 403 |
| 未認証アクセス | 全エンドポイント 401 |
| 管理者専用API | 店舗・ベンダー・本部から 403 |

**評価: 良好。** 特に「他社IDを指定したら黙って自分のスコープに読み替える」のではなく
明示的に 403 を返す設計は、実装ミスの発見しやすさの点で適切。

## 4. 検出した欠陥と是正

### 4-1【重大】発注確定が同時実行ですべて成功する

**再現**: 3並列で `POST /api/orders/{id}/confirm` → **3件とも 200**。

**原因**: `order.status not in {DRAFT, PLANNED}` で判定してから UPDATE していた。
3スレッドが同じ `DRAFT` を読んだ時点で全員が判定を通過する。

**影響**: 確定通知の多重送信、`confirmed_by` の上書き、ステータス履歴の重複。

**是正**: 条件付きUPDATEの更新行数で勝者を決める方式に変更（`claim_status_transition`）。

```python
UPDATE orders SET status='CONFIRMED', ... WHERE id=? AND status IN ('DRAFT','PLANNED')
```

**是正後**: `[200, 409, 409]` → 成功1件。確定履歴も1件のみ。

---

### 4-2【重大】変更申請の承認が同時実行ですべて成功する

**再現**: 本部3人が並列承認 → **3件とも 200、承認履歴が3件記録**。

**影響**: 承認者が上書きされ、誰が承認したのか監査証跡から追えなくなる。
「言った・言わない」を防ぐという本アプリの目的を直接損なう。

**是正**: 4-1と同じ方式（`ChangeRequest.status == PENDING` を条件にUPDATE）。

**是正後**: `[200, 409, 409]` → 成功1件、承認履歴1件、数量反映も1回のみ。

---

### 4-3【重大】ロストアップデート（後勝ちで静かに上書き）

**再現**: 店舗担当者2人が同じ発注画面を開き、Aが10ケース、Bが20ケースで保存
→ **両方 200、最終値は20**。Aの入力は警告なく消える。

**影響**: 仕様書 §7「データが静かに上書きされる状態を許可しない」に明確に違反。

**是正**:
- `orders.version` を追加し、`PUT /api/orders/{id}` で **version を必須化**
- 判定は「読んで比較」ではなく条件付きUPDATE
  （同じ値を読んだ2つが両方通過するのを防ぐため）
- フロントは 409 をトーストではなく **確認ダイアログ** で表示し、
  「最新の内容を読み込む」「入力を保持したまま戻る」を選ばせる

**是正後**: 逐次でも10並列でも成功は1件のみ。先に保存した内容が守られる。
実ブラウザでも競合ダイアログの表示を確認済み。

---

### 4-4【重大】ベンダー回答後も数量変更・取消ができる

**再現**: ベンダーが「全数納品」と回答して納品確定（DELIVERED）になった発注に対し、
締め前であれば店舗が数量を 2→77 ケースに変更でき、取消もできた。

**原因**: `update_order` が締め時間と取消済みしか見ておらず、
`EDITABLE_STATUSES` の判定が入っていなかった。

**影響**: ベンダーの回答（納品確定・欠品・一部納品・代替提案）の前提が
無断で崩れる。ベンダーは回答済みの数量で出荷準備をしているため実害が出る。

**是正**:
- 直接編集を許すのは 下書き / 発注予定 / 発注確定 / ベンダー未確認 / ベンダー確認済み のみ
- 回答済み（一部納品・欠品・代替提案・納品確定）は締め前でも 409
- 納品確定済みの取消は店舗から不可（本部・管理者は可）
- `GET /api/orders/{id}/editable` にも反映し、画面からボタンを消す

---

### 4-5【重大】発注番号の採番競合でサーバーエラー

**再現**: 10並列で発注登録 → **成功1件、9件が IntegrityError で 500**。

**原因**: 既存件数を数えて次番号を決めるため、同時登録が同じ番号を掴む。
UNIQUE制約違反をそのまま外へ流していた。

**是正**: SAVEPOINT で受け止め、番号を採り直して再試行（最大8回）。

**是正後**: 10並列すべて 201、発注番号の重複なし。

---

### 4-6【中】ログアウト後もトークンが有効

**再現**: ログアウト後、手元に控えたトークンで `GET /api/auth/me` が 200。

**是正**: トークンID（`jti`）を `revoked_tokens` に登録して個別失効。
他端末のセッションは維持される。

> 当初は「基準時刻より前に発行されたトークンを無効」とする実装にしたが、
> JWT の `iat` が秒単位のため **ログアウトと同じ秒に発行されたトークンを取りこぼす**
> ことがテストで判明したため、jti による個別失効に変更した。

---

### 4-7【中】パスワード変更・権限変更後も旧セッションが有効

**再現**: 他端末のセッションがパスワード変更後も使えた。
所属店舗を変更しても旧権限のセッションが生きていた。

**是正**: `users.session_version` を追加。トークンに `sv` を埋め込み、
不一致なら 401。パスワード変更・再設定・権限や所属の変更・アカウント停止で +1。

> 時刻ベースの実装も試したが、切り上げると発行直後のトークンが未来の `iat` を持ち、
> PyJWT 2.7 が `ImmatureSignatureError` で拒否した。
> 時刻に依存しない版数方式に変更して解決。

| 通知 | 条件 |
|---|---|
| 締め24時間前 / 1時間前 | 締め時刻が現在から24時間 / 1時間以内 |

## 11. 監査所見

**良かった点**

- 権限・データ分離は監査前から堅牢だった。総当たり検証で漏洩ゼロ。
  「他社IDを指定したら黙って読み替えるのではなく403」という設計判断が適切。
- 履歴の追記専用設計と、削除APIを設けない方針が徹底されていた。
- 発注明細が登録時点のスナップショットを保持しており、マスタ変更の影響を受けない。
- タイムゾーンの扱い（内部UTC・判定と表示は日本時間）が一貫していた。

**弱かった点**

- **単一ユーザーの操作を前提に実装されていた。** 権限分離には注意が払われていた一方、
  同時操作の観点がほぼ全面的に抜けていた。確定・承認・更新・採番のすべてで競合が起きた。
- **ステータス遷移が「締め時間」だけで守られていた。** 業務上の状態
  （ベンダーが回答済みか）による制御が入っていなかった。
- 入力値検証が「必須かどうか」に偏り、**値の妥当性**（上限・過去日・負数）の検査が
  一部抜けていた。

いずれも「正常系は動くがマルチユーザーの異常系が未検証」という共通点がある。
是正にあたっては、修正と同時に**並列実行で再現するテスト**を追加し、
同種の欠陥が再び入り込まないようにした。
